# 현장 운영 가이드

## 운영 상태

질문 상태는 `접수(received)`, `확인 중(reviewing)`, `답변 완료(answered)` 세 단계입니다. 운영진 화면은 상태별 열, 유형 필터, 질문·연락처 상세, 답변 입력, 변경 이력을 분리합니다.

권한은 다음처럼 운영합니다.

| 역할       | 할 수 있는 일                                |
| ---------- | -------------------------------------------- |
| `viewer`   | 전체 질문과 연락처 읽기, 읽기 전용 화면 사용 |
| `operator` | 읽기, 상태 변경, 답변 작성                   |
| `owner`    | operator 기능과 운영진 멤버십 관리 절차 수행 |

멤버십 변경은 현재 UI가 아니라 검토된 SQL/운영 절차로 수행합니다. 임의 사용자가 자기 계정을 운영진으로 바꿀 수 없습니다.

운영진 화면은 인증 정보를 브라우저 저장소에 영구 보관하지 않습니다. 로그인한 탭이 보이는 동안 인증 세션을 갱신하고 60초마다 질문 목록을 확인하며, 숨겨진 탭에서는 자동 확인을 중단합니다. 세션이 만료되면 저장을 반복하지 말고 안내에 따라 다시 로그인합니다.

## 행사 전 체크리스트

1. 일정·서명 시간·협의실·주소·전화번호를 행사 담당자 2인이 교차 확인합니다.
2. `status: draft`를 유지한 채 GitHub Pages 체크포인트에서 360px 휴대전화와 데스크톱을 확인합니다. 자동·실기기 검증을 통과하면 참가자 접수를 열지 않는 `status: ready`로 승격합니다.
3. Supabase staging에서 익명 제출, 속도 제한, 상태 조회, 운영진 403/권한을 시험합니다.
4. 시험 질문 한 건으로 Discord의 새 질문 알림과 이메일 답변 완료 알림을 각각 확인합니다.
5. Turnstile hostname과 `ALLOWED_ORIGINS`에 최종 호스트만 남깁니다.
6. 후보 짧은 주소를 실제 휴대전화의 Wi-Fi와 모바일 데이터에서 모두 엽니다.
7. 새 QR을 인쇄 테스트하고 스캔 결과·대비·오류 복구 동선을 확인한 뒤에만 QR 상태를 `active`로 바꿉니다.

## 접수 개방과 종료

프런트 상태와 데이터베이스 접수 상태를 별도 안전장치로 운영합니다. `ready`에서는 사이트와 QR을 사용할 수 있지만 질문 제출 버튼은 열리지 않습니다.

행사 당일 접수 개방 순서는 다음과 같습니다.

1. 현장 운영자가 `/admin/`에 로그인하고 질문 목록을 불러올 수 있는지 확인합니다.
2. 프런트가 `ready`인 상태에서 Supabase의 `events` 행 중 `2026-sk.is_active`를 `true`로 변경합니다. 공개 폼은 아직 닫혀 있습니다.
3. `src/config/events/2026-sk.ts`의 프런트 상태를 `published`로 변경해 PR 검증과 Pages 배포 성공을 확인합니다.
4. 고정 QR로 접속해 `운영 점검`으로 식별되는 질문 한 건을 제출하고, 비공개 상태 조회·운영진 화면 반영·Discord 새 질문 알림을 확인합니다. 이메일을 남긴 경우 답변 완료로 바꾼 뒤 이메일도 확인합니다.
5. 검토된 운영 절차로 점검 질문을 삭제하고 질문 건수가 0인지 확인한 뒤 참가자에게 QR을 안내합니다.

행사 종료 때는 순서를 반대로 적용합니다. 먼저 `is_active=false`로 새 저장을 막고, 미답변 질문을 정리한 다음 프런트를 `archived`로 배포합니다. 접수 개방·종료 중 하나라도 실패하면 다른 스위치를 억지로 맞추지 말고 잠긴 상태로 되돌린 뒤 원인을 확인합니다.

현재 활성 owner가 1명이므로 기술적으로 운영할 수 있지만 계정·기기 장애에 대한 단일 실패 지점이 있습니다. 두 번째 운영자는 권장 사항이며, 추가하지 못한다면 행사 중 owner가 로그인 가능한 기기와 복구 수단을 계속 확보해야 합니다.

## 행사 중 처리

- 공지 변경은 정적 콘텐츠 PR로 검토·배포하고 현장 안내가 웹보다 최신이면 웹에 그 사실을 표시합니다.
- 접수 질문은 우선 유형과 긴급도를 확인하고, 담당자가 보기 시작하면 `확인 중`으로 바꿉니다.
- 상태별 건수와 필터를 사용하되 현장 교대 때는 `전체` 목록과 마지막 확인 시각을 함께 확인합니다.
- 답변에 학생·학교·강사의 개인정보를 재기재하지 않습니다.
- 해결 내용을 입력한 뒤 `답변 완료`로 바꾸면, 이메일 알림을 선택한 참가자에게만 완료 알림을 시도합니다. 이메일에는 질문·답변 본문을 넣지 않습니다.
- 알림 실패는 질문 상태 저장을 되돌리지 않습니다. `notification_deliveries`에서 실패 원인을 확인하고 필요하면 다른 채널로 수동 안내합니다.

## 장애 대응

| 상황                     | 현장 대응                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 개별 Pages 배포 장애     | 마지막 정상 배포를 유지하고 Pages workflow를 재실행                                                           |
| GitHub Pages 전체 장애   | 자동 전환 없음; 승인·검증된 독립 비상 페이지가 있을 때만 고정 주소의 목적지를 수동 변경하고, 없으면 현장 안내 |
| 질문 API 장애            | 폼에 연결 불가를 표시하고 핵심 일정은 계속 제공; 운영진 현장 안내로 대체                                      |
| Discord·이메일 알림 장애 | 운영진 화면과 접수번호 상태 조회를 우선 사용하고, `question_notification_deliveries`의 오류 코드를 확인       |
| 스팸 증가                | rate limit을 조정하고 Turnstile 분석·hostname·origin을 재확인                                                 |
| 개인정보 오입력          | 접근을 제한하고 사고 기록 후 원문/연락처 삭제 절차 수행                                                       |
| 계정 의심                | 해당 Auth 세션 폐기, 멤버십 비활성화, secret 회전, 감사 이력 확인                                             |

## 행사 종료

1. 질문을 더 받지 않도록 행사 상태를 종료하고 폼을 읽기 전용 안내로 전환합니다.
2. 미답변 질문을 모두 정리하고 필요한 참가자에게 완료 알림을 보냅니다.
3. 정한 보존 기간에 맞춰 연락처와 질문 원문을 삭제합니다.
4. 재사용할 행사 설정은 개인정보 없이 템플릿화합니다.
5. 기존·신규 QR 리디렉션 유지 현황과 접근 로그의 이상을 확인합니다.
